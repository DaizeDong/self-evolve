# self-evolve 的方法与能力边界

self-evolve 用同一条流程组织改进：reflect 诊断已有证据，propose 提出修改，
evaluate 取得可观察结果，再由代码决定接受、拒绝或交给人工复核。
一次 ACCEPT 说明候选满足了本轮已配置的判据；实际效果仍受测试覆盖、数据质量和运行环境限制。

## 先确定怎样验证改进

A、B、C 表示证据来源。先给目标写出可检查的要求，再确定当前实现能否提供相应证据。

| 路径 | 当前证据 | 使用条件 |
| --- | --- | --- |
| A | 测试逐项结果及父代配对 | 基线可复现，测试信号可用，能观察修改的影响 |
| B | 冻结事实身份及独立核验 | 来源可访问，候选和父代可按同一身份核验，留出集完整 |
| C | 调用方提供的回归与一致性记录，以及 judge 结果 | 有真实观测可供校验；缺失时必须报告不可用 |

自动生成场景和 rubric 的 scenario-eval 尚未实现。当前主循环没有 C 路的回归回放
及一致性测量生产者，不能用历史决策或空列表冒充这些观测。纯 C 默认需要人工复核。
PROFILE 可以识别组合标签，但主循环明确拒绝 A+B，不能把标签识别当成组合执行已完成。
详见 [信号参考](../reference/signal-providers.md)。

## 保持证据可核对

1. **记录实际结果。** 失败、超时、未收集到测试、来源不可访问，都应各自保留原因。
   不能把准备完成、退出码为零或空报告直接算作效果通过。
2. **保留比较对象。** A 按父代任务身份配对；B 保留冻结的事实身份与覆盖分母。
   删除候选中的任务或事实不能使它从比较中消失。
3. **区别各路判据。** A 有逐任务 no-regression 硬门，随后还要满足统计接受条件。
   B 使用完整正负配对、净增益和专属门，不承诺每一项都不退化。
4. **记录实际 provider。** 并行调用、不同入口名和不同请求标签本身不能证明模型独立。
   judge 的家族判断以实际返回的 provider 证据为准。
5. **保留拒绝与暂停。** 证据不足时继续收集或交给人工判断，不降低阈值换取 ACCEPT。

e-process 的解释依赖其统计假设、输入身份、独立性和计分方式成立。它不能单独证明
测试充分、业务需求满足，或有限案例之外的能力已经提升。

## 隔离与数据

发给 reflect、propose 和 judge 的结构化 prompt 会排除核验真值。留出集与可见集分开，
抽检时核对冻结路径、数量、摘要及不相交关系。共享账户下的目录分开、临时 cwd、
只读文件标志和 Python 检查都不等于操作系统权限隔离；需要这种保证时，应另行验证执行环境。

运行历史、候选工作树、报告及 agent 临时目录放在验证为 PRIVATE 的伴生 Git 仓中。
公开技能仓提供未初始化的工具和合成样例。写入找不到合法私有目录时失败，不回退到工具仓。

## 在新目标上开始

1. 明确目标目录、改进要求和可接受的修改范围。
2. 运行 `doctor`，检查基线、私有数据目录和当前能力。
3. 为 A 或 B 准备可复现的证据；只有主观目标时，先补测量或安排人工复核。
4. 初始化运行并冻结 profile，执行有限轮次，检查原始结果和失败原因。
5. 在同一候选上完成回归与独立复核，再按用户授权处理安装、合并或发布。

入门命令见 [README](../README.md)。自举保护见 [self-boot](modules/self-boot.md)，
统计契约见 [acceptor_math](../reference/acceptor_math.md)。
